# Архитектура: верхний уровень

## Проблема

Несколько AI-агентов параллельно (CLI, GUI, IDE-встроенные, web-based) — у каждого своя память и свои правила. Через месяц:

- Информация дублируется
- Правила расходятся
- Контексты смешиваются
- При старте сессии агент грузит много «на всякий случай»

## Идея

**Один файловый vault** для всех агентов. Все агенты обращаются как к набору markdown-файлов через файловую систему.

```
master-vault/
├── 00-home/        ← точка входа (для человека)
├── agents/         ← правила работы агентов
├── memory/         ← поведенческие правила (auto-load слой)
├── work/           ← рабочий контекст
├── personal/       ← личный контекст
├── cowork/         ← computer-use / file-org / demo
├── _templates/     ← Obsidian templates (по желанию)
└── _archive/       ← read-only снэпшоты
```

## Уровень разделения

**Секции (work/personal/cowork)** — контексты которые **не должны смешиваться**. Sessions, knowledge, artifacts изолированы per section. Триггеры что относится к какой секции — определяешь сам в своих правилах.

**Папки внутри секций** — `knowledge/`, `sessions/`, `artifacts/` — создаются по мере появления первого файла. Заранее пустые placeholder-папки не создаются.

## Стандарт per-agent

Каждый агент описывается одним файлом `agents/<agent-id>.md` по стандарту в `agents/_standard.md`. Стандарт фиксирует:

- Frontmatter (agent_id, status, tools, context_limit, ...)
- 6 обязательных секций (When to read / Token economy / Where to write / Session save / Specifics / Pre-flight)
- Naming convention

Это позволяет добавлять новых агентов единообразно — копируешь шаблон, заполняешь секции.

## Memory как auto-load слой

Папка `memory/` отдельно от секций. Сюда складываются **поведенческие правила** — то что должно влиять на каждую будущую сессию агента.

| Где | Что | Когда |
|---|---|---|
| `memory/` | Правила поведения (auto-load) | Урок для будущих сессий |
| `<section>/knowledge/` | Факты, решения, история (selective load) | Конкретная информация по запросу |

Тест перед записью: «это должно влиять на КАЖДУЮ будущую сессию?» Да → memory. Нет → knowledge.

Конкретная структура memory (подпапки feedback / project / reference и т.п., способ auto-load) — определяешь под своего основного агента.

## Token-economy

Главное правило при auto-load — **грузить мало**. При старте сессии агент должен получить **только**:

1. `agents/<его-id>.md` (правила конкретно его)
2. Базовые общие правила (если есть)

Всё остальное — selective через grep/glob по триггеру в сессии. Это удерживает cold-start cost в разумных пределах.

## Sync layer

Единая память живёт на нескольких машинах (рабочий комп, сервер с агентами, возможно телефон). Слой синхронизации между устройствами — отдельный архитектурный компонент, **не зашитый** в шаблон (выбор зависит от инфраструктуры).

Важно: git закрывает версионирование (ручной `pull`), но **не** realtime-синхронизацию файлов. Для живого sync нужен отдельный механизм (Obsidian Sync / Syncthing / облако). При файловом sync — обязательно исключать `.git/` чтобы не повредить репозиторий.

Варианты, топология и грабли — в [SYNC.md](SYNC.md).

## Что НЕ зашито в шаблон

Этот репо — только верхний уровень. **Решаешь сам:**

- Сколько R-правил и какие именно (рекомендация: 5-10 коротких)
- Структура `memory/` (плоская / с подпапками / своя)
- Какие agents/<id>.md писать первыми (зависит от какими агентами реально пользуешься)
- Как именовать секции (work/personal/cowork — это пример; можно client-A/client-B/learning, что угодно)
- Какие Obsidian-templates делать в `_templates/`
- Какой OS-level bootstrap для каждого агента (skill / system prompt / custom rules)
- Слой синхронизации между устройствами (см. [SYNC.md](SYNC.md))
